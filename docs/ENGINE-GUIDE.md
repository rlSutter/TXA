# The TXA Engine Implementation Guide

Generated by `tools/gendocs.py`; do not edit by hand. For anyone writing a TXA engine for another machine, or maintaining the TI engine. A compiled TXA story is meant to run anywhere there is an engine, as Infocom's story files did; the TI-99/4A engine is the first, and the Python reference VM (`tools/txc/txvm.py`) is the definition of correct behaviour.

## What a port is

A VM for the opcodes, plus an input/output layer: printing with word wrap, reading a line, saving and restoring, and optionally pictures, styles and sound. Everything else, the parser and the whole standard library included, is TXA code inside the story image, so every engine runs the same parser without reimplementing it.

## The rules

From the specification's portability rules, which every decision has been checked against:

1. **No machine detail in the image.** Opcodes say what happens ("print this", "show picture 3"), never how a screen or chip does it.
2. **Optional features degrade silently.** PICTURE, STYLE, SOUND and MUSIC are requests: an engine without pictures shows none, one without bold prints plain text, one without sound stays quiet.
3. **Pictures are converted per platform at build time.** The image names pictures by number; their data belongs to each platform's build.
4. **Screen width belongs to the engine.** Word wrap is the engine's job; 40 or 80 columns both work.
5. **Memory is the engine's business.** Stories are up to 256K; how an engine reaches them (SAMS paging, banking, flat memory) never shows in the image.
6. **Save files have one format**, so a game saved on one machine restores on another.
7. **Text is plain ASCII** in the image.
8. **No engine-specific opcodes.** A capability one engine has becomes an optional feature, defined for every engine.

## The VM

The machine, the story image's layout and every opcode are in the *Technical Reference* (generated from `tools/txc/opcodes.py`, the single definition). In brief: 16-bit signed words; a value stack and call frames of up to 16 locals; 240 globals; routines and strings named by packed address (byte address / 4); a dynamic area at the image's start (at most 16384 bytes) that saves, UNDO and RESTART work on. RESTART reloads the dynamic area from the image as it was loaded; the engine must keep that copy.

## The input and output layer

These opcodes are the engine's own work; their meanings, from `opcodes.py`:


| Opcode | What the engine must do |
| --- | --- |
| `PRINTS` | Print the packed string p. |
| `PRINTV` | Print the packed string on the stack (0 prints nothing). |
| `PRINTN` | Print a signed number. |
| `PRINTO` | Print o's short name. |
| `PRINTC` | Print one character. |
| `NEWLINE` | End the line. |
| `STYLE` | Text style from now on: 0 roman, 1 bold, 2 underline, 4 reverse, 8 centred lines (each line written in the middle of the screen; the engine knows its width), added together to combine.  An engine without a style shows plain text. |
| `PRINTA` | Print o's name with an article: 0 'the', 1 'The', 2 'a', 3 'A' (plural, proper and vowel rules). |
| `READ` | Read a command line into text array t (t(0) = length, then one character per element, lower case) and TOKENIZE it into parse array p; push the word count. |
| `READKEY` | Wait for a key; push its code. |
| `FRESH` | End the line if anything has been printed on it since the last new line. |
| `TOKENIZE` | Split the text in array t into words: p(0) = count, then for each word its dictionary number (0 if unknown), its first character (index into t) and its length. Words are runs of characters other than space, comma and period; a comma or period is a word by itself. Matched on 12 characters. Words past the space in p are dropped. |
| `RANDOM` | A random number from 1 to n; n <= 0 reseeds (0 at random, -s with s) and pushes 0. |
| `QUIT` | End the game: back to the title screen. |
| `RESTART` | Reload the dynamic area and start again. |
| `SAVE` | Save the game to the file named in text array t (t(0) = length, then characters); push 1 if saved, 0 if not.  When a RESTORE later loads the file, execution continues here with 2 pushed instead.  The file is in the save format below, the same on every engine. |
| `RESTORE` | Restore the game saved in the file named in text array t: execution continues after the SAVE that wrote it, which pushes 2.  If the file is missing, damaged, or from another story or release, push 0 and change nothing. |
| `UNDOSAVE` | Take an undo snapshot (the dynamic area, the stacks, the PC and SELF) and push 1.  When an UNDO later goes back to it, execution continues here with 2 pushed instead. |
| `UNDO` | Go back to the newest snapshot, removing it (so a second UNDO goes further back): execution continues after its UNDOSAVE, which pushes 2.  If there is none, push 0 and carry on.  An engine keeps at least one snapshot; the TI keeps 28K of differences (over a hundred typical turns), starting again when they fill. |
| `STATUS` | Draw the status line: room r's short name (0: "Darkness") on the left; on the right "Score: s  Moves: m", or "Moves: m" when s is -1. An engine without a status line ignores it. |
| `CLS` | Clear the text window (a partly written line is written first); the next line starts at its top.  An engine without a screen may just start a new line. |

Notes from the TI engine: printing wraps words at the screen's width and pauses with [MORE] when a screenful has scrolled without a key; READ lowers the case of what it stores and allows editing and a command history (how is the engine's choice); TOKENIZE's dictionary lookup matches the first 12 characters; STATUS draws the status line in the engine's own way.

## Optional features

| Opcode | What the engine must do |
| --- | --- |
| `PICTURE` | Show picture n (0 hides the pane). |
| `SOUND` | Play sound effect n once, over any music (an engine without sound stays silent). |
| `MUSIC` | Play tune n (looping if it loops); 0 stops the music; the tune already playing goes on.  An engine without sound stays silent. |
| `DEBUG` | Push 1 if the story is running under test-play (bit 0 of the header's flags word, set by the workbench in its copy of the story), else 0: the library's debug verbs work only then. |
| `RECORD` | Record the commands the player types from now on to script file n (0-9; on the TI, the game's prefix + R + n as a DV80 file on its device); n < 0 stops. Push 1, or 0 if the file cannot be made. Starting a recording stops a replay. |
| `REPLAY` | Take the commands READ reads from script file n (as RECORD made it) instead of the keyboard, each echoed as if typed, until the file ends (then the keyboard again); n < 0 stops. Push 1, or 0 if there is no such file. Starting a replay stops a recording. |

An engine without a feature still accepts its opcode and does nothing (DEBUG pushes 0; RECORD and REPLAY push 0, so the library says the file could not be made or found).

## Saving

The save file's format is given byte for byte in the *Technical Reference*. Follow it exactly: a save from one engine must restore on any other. RESTORE refuses a file whose checksum or release differs from the story's.

## Proving an engine correct

The Python VM is the reference. An engine is correct when it gives the same transcript for the same story and commands:

- **The sample game**: `samples/lamplight.txa` with its walkthrough `samples/lamplight.walk` (won with full marks); the reviewed transcript is what the Python VM prints.
- **The tutorial's game**: `samples/tutorial/ferry1-5.txa`.
- **The corpus**: the stories under `tests/txa/` with their command scripts, which exercise every opcode and the parser's corners (`tests/txc_run_test.py` runs them on the Python VM; `tests/m2_engine_test.py` compares the TI engine's output with it).
- **Saves**: a save written by the engine must restore in the Python VM and the reverse (`tests/m4_save_test.py` does this for the TI).

For RANDOM, the reference VM's generator and seed rule are in `txvm.py`; an engine whose numbers differ still plays correctly, but its transcripts can only be compared where the story seeds the generator.

## The TI engine

The TI-99/4A engine (`src/`, TMS9900 assembly) is one implementation: its memory, SAMS pages, video memory and F18A settings are in the *Technical Reference*; `docs/CONTEXT.md` and `plan.md` record how it was built and why.
