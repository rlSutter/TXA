# TXA Technical Reference

Generated by `tools/gendocs.py` from the source; do not edit by hand. The tables and format descriptions are read from the files that define them (`tools/txc/opcodes.py`, `src/defs.a99`, `src/wovl.a99`, and the tools' own descriptions), so this reference changes when they do.

## 1. The story image

A story is one image of at most 256K: a 64-byte header, the dynamic area (the object table, property tables, globals and arrays: the part a game changes, and the part saved), then the static tables (dictionary, grammar, actions, text substitutions), which must lie in the first 64K because the header holds 16-bit offsets to them, then the routines and strings, each on a 4-byte boundary and named by packed address (byte address / 4). All words are big-endian. The magic is `TXA1`, format version 1.

### The header

| --- | --- | --- |
| 0 | `magic` | 4 bytes 'TXA1' |

| 10 | `image_len_hi` | image length in bytes, high and low words |
| 12 | `image_len_lo` | (the low word of the image's length) |
| 14 | `dynamic_len` | bytes from 0 to the end of the dynamic area |
| 16 | `objects` | offset of the object table |
| 18 | `object_count` | the number of objects |
| 20 | `props_start` | offset of the first property table |
| 22 | `globals` | offset of the globals (240 words) |
| 24 | `arrays` | offset of the array directory |

| 30 | `actions` | offset of the action table |

### Objects and properties

Each object has a 14-byte entry: parent, sibling and child (words: object numbers, 0 for none), 6 bytes of attributes (48, the first attribute in the high bit of the first byte), and the offset of its property table. A property table starts with the object's short name (a packed string address, 0 for none), then its properties in ascending number, each a byte holding the number and its kind, a count byte, and the values; a zero byte ends the table. The kinds: >00 words (count words follow), >40 a string (one packed address), >80 a routine (one packed address).

### Globals, arrays and the dictionary

The globals are 240 words (variables 16-255). The arrays have a directory (a count, then each array's offset and length in words) and then their data; the parser's tables (VERBTAB, GRAMTAB, ACTSUB, DICTVERB) are arrays the compiler fills. The dictionary is a count, then 14-byte entries in byte order: 12 characters, zero padded; a flags byte (1 noun, 2 verb, 4 preposition); the verb's number. A word's number is its place in the dictionary, from 1.

### Text

A string is a run of bytes ended by 0: 10 is a line break, 32-126 themselves, and >80->FF the text substitution with that index (0-127), whose words the substitution table holds (128 offsets from the table's start, 0 for unused, then the words, each ended by 0). The compiler chooses the substitutions from the game's own strings.

### The dynamic area and the checksum

The dynamic area is at most 16384 bytes (the engine keeps an UNDO copy of it in four SAMS pages). The checksum is the sum of every byte after the header, mod 65536; a save file names the checksum and release of the story it belongs to.

## 2. The instruction set

```
- Values are 16-bit words, signed for arithmetic and comparison.
- A value stack and a call stack.  Each call frame holds up to 16 local
  variables (parameters first), the return address, the caller's stack
  height and the caller's SELF.
- Variables are numbered 0-255: 0-15 are the current frame's locals,
  16-255 are the globals (global n is variable 16 + n).
- SELF is a register: set by RUNPROP/CALLPROP to the object whose
  property is running, put back when that routine returns.
- Routines and strings start on 4-byte boundaries and are named by
  16-bit *packed addresses* (byte address / 4), reaching a 256K image.
- A routine starts with one byte, its local count (parameters
  included); its code follows.  Locals past the arguments start at 0.
- Jumps carry a signed 16-bit offset from the byte after the jump.
- Operands follow the opcode: b = one byte (unsigned unless noted),
  w = one word (high byte first), j = a jump offset, p = a packed address.

Stack notation: "a b -> c" pops b then a and pushes c.
```

## 3. File formats

### The save file

```
All words big-endian; "long" = high word then low word.
  'TXS1'
  word  format version (SAVE_VERSION)
  word  the story's checksum (header)      word  its release
  word  the dynamic area's length
  long  the PC: the byte after the SAVE instruction (a story address)
  word  SELF
  word  n, the value stack's depth in words; then n words
  word  m, the number of call frames; then each, outermost (Main) first:
    long  return address (>FFFFFFFF: returning ends the game)
    word  the caller's stack depth, in words, once the arguments are taken
    word  the caller's SELF
    word  k, the local count; then k words
  the dynamic area, as XOR against the story's original dynamic area,
  run-length coded: >00->7E n: n+1 unchanged bytes; >80->FF n: n->7F
  changed bytes follow (XOR values); >7F: the end
  word  the sum of every byte before it, mod 65536
```

### Run-length packing (pictures)

```
rlepack.py - the picture run-length format (decoded by src/rle.a99).

   >00->7F  n: the next n+1 bytes are literal (1-128)
   >80->FE  n: the next byte repeats n - >7D times (3-129)
   >FF      end
Runs of three or more equal bytes become repeats; everything else is
gathered into literal runs.  unpack() is the reference decoder the tests
check the assembly decoder against.
```

### The picture area

```
txpics.py - pictures for the TI build: PNG to the F18A bitmap layer.

A story declares pictures by name and file (PICTURE Harbour "HARBOUR");
the story image itself holds only their numbers (portability rule 3).
This tool, part of the TI build, converts each picture's PNG (or TI Artist
picture, NAME_P and NAME_C: tools/tiartist.py) and lays the results out as
the picture area, which the engine finds in SAMS right
after the story.

Formats (the F18A bitmap layer, 96 rows high, 256 screen pixels wide):
  2 - 256 x 96, 2 bits a pixel, 4 colours: chosen when the PNG uses at
      most four colours (sharp line art)
  4 - 128 x 96 "fat" pixels, 4 bits a pixel, 16 colours: otherwise (the
      PNG is scaled to 128 x 96 and reduced to 16 colours)
Either way the pixel data is 6144 bytes, most significant pixel first,
then run-length packed (tools/rlepack.py).  Each picture carries its own
palette (12-bit RGB), loaded into F18A palette entries 32-47 when shown.

The picture area:
  word  count
  count x long  each picture's offset from the area's start
  then each picture: byte format (2 or 4), byte colours (4 or 16),
                     that many palette words (>0RGB), the packed pixels
The engine reads it through SAMS window D (src/picture.a99).
```

### TI Artist pictures

```
tiartist.py - TI Artist pictures for TXA (M6 part 9): the reference the
workbench's import (I) must match byte for byte.

A TI Artist picture is two PROGRAM files of 6144 bytes each, NAME_P (the
pattern table) and NAME_C (the colour table): the 9918A's bitmap mode,
256 x 192 pixels in 8 x 8 cells, two of the TI's 16 colours for each
8-pixel row (foreground in the high nybble).  On a PC they usually carry a
128-byte TIFILES header, which is skipped.

A TXA picture (tools/txpics.py) is format 4: 128 x 96 "fat" pixels, 16
colours, shown in the 96 rows above the text.  So the picture is fitted
one of two ways (Rebecca, 28 October 2026: both, crop the default):
  crop ROW   the 96 rows from ROW (0-96, even), full width: the proportions
             kept, the rest of the picture left out
  squeeze    the whole picture at half height: each pair of rows becomes
             one
Then each pair of pixels becomes one fat pixel.  The rules, simple enough
for the TI:
  two pixels (a pair across, or in squeeze a pair down): the first, unless
  it is background (colours 0 and 1, transparent and black) and the second
  is not; then the second.
The palette is the TI's own 16 colours (12-bit), transparent shown black;
the pixels are packed with tools/rlepack.py.

A picture's choice is kept in NAME_T beside it (a TI file name cannot hold
a full stop), one line: "crop 48" or "squeeze"; with none, crop 48 (the
middle).  On the TI it is a DIS/VAR 80 file; on a PC, plain text.

  python3 tools/tiartist.py NAME [crop ROW | squeeze]   writes NAME.png, the preview
```

### Music and sound effects

```
txsound.py - music and sound effects for the TI build.

A story declares tunes and effects by name and file (MUSIC Harbour
"HARBOUR", SOUND Horn "HORN"); the story image holds only their numbers
(portability rule 3).  This tool, part of the TI build, compiles each
file's notation into events for the TMS9919, lays them out as the sound
area (in SAMS after the pictures), and is the reference player the TI
engine's player is tested against, write for write.

THE NOTATION (one .mml text file per tune or effect)
  ! a comment, to the end of the line
  TEMPO 90          quarter notes a minute (default 120)
  LOOP              the tune starts again when it ends (music; effects
                    usually play once)
  A: ...  B: ...  C: ...   the three tone voices; N: ... the noise voice.
                    A voice may take several lines; they join up.
In a voice:
  c d e f g a b     a note; then + (or #) sharp, - flat; then a length
                    (1 2 4 8 16 32: whole, half ... thirty-second) and
                    dots (each adds half again).  Middle C is c4.
  r                 a rest, with a length the same way
  o4  < >           the octave (1-7); one down, one up
  l8                the default length (dots allowed: l2. in 3/4 time)
  v12               the volume, 0 (silent) to 15 (loudest)
  @4                decay: the volume falls one step every 4 frames
                    while a note sounds (@0: none, the default)
  &                 ties the next note to this one (no new attack)
  [ ... ]3          plays what's inside 3 times (2 if no number)
  |                 a bar line, for the eye only
On the noise voice the notes are k (a low drum: periodic noise), s (a
snare: white noise), h (a hi-hat: high white noise), x (a high buzz:
periodic), or n0-n7 (the chip's noise types); lengths, r, v, @ as above.

THE EVENTS (each voice a byte stream)
  >01 pp pp dd   a tone: period (10 bits), then dd frames (1-255)
  >02 dd         a rest of dd frames (silent)
  >03 vv         volume vv (0-15) for the following notes
  >04 ee         decay: one step every ee frames (0: none)
  >05 tt dd      noise type tt (0-7) for dd frames
  >06 dd         hold: the note goes on dd more frames (long notes, ties)
  >00            the voice's end
A frame is a sixtieth of a second (the VDP's frame flag).

THE SOUND AREA
  word  M (tunes)   word  S (effects)
  (M+S) x long  each item's offset from the area's start: tunes first,
                then effects (MUSIC n is item n, SOUND n item M+n)
  each item: byte voices, byte flags (1: loops), then per voice
             byte channel (0-2 tone, 3 noise), word its stream's offset
             from the item's start; then the streams

THE PLAYER (the same on the TI: src/sound.a99)
Once a frame, for each voice in order (music voices, then effect voices):
  if it is waiting: one frame less; if a note sounds with a decay, the
  decay count goes down and at 0 restarts and the volume falls a step
  (written to the chip); then, if the wait has run out, events are read
  until one takes time (a tone, a rest, noise or hold) or the voice ends.
  A tone writes the period (two bytes) and the volume (one byte); a rest
  writes silence; noise writes the type and the volume.  At its end a
  voice of a looping item starts its stream again; otherwise it falls
  silent and stops.  While an effect voice uses a channel the music voice
  on it writes nothing; when the effect voice ends, the music voice's
  last period and volume are written back.
```

The notation they are written in, TXA music notation 1.0, is described in `docs/MUSIC.md`.

### Workbench files

- **Source files**: DIS/VAR 80, one line a record.
- **Story files** PREFIX + S + two digits: the image in 4K PROGRAM files.
- **Picture files** PREFIX + P + two digits: the picture area in 4K PROGRAM files.
- **Music files** PREFIX + M + two digits: the sound area in 4K PROGRAM files.
- **Engine files** PREFIX + 1 to 5: the engine, E/A 5 (memory image) files; load the first.
- **Scripts** PREFIX + R + a digit (RECORD, REPLAY): DIS/VAR 80, one command a record.
- **Saved games**: one PROGRAM file, the save file above.
- **NAME_T**: a TI Artist picture's fitting, one DIS/VAR 80 line, `crop N` or `squeeze`.
- **DSK1.TXAOPT**: the workbench's options, DIS/VAR 80 lines `colours N` (0-4), `font normal` or `font bold`, `library DSK2. DSK3.`.

## 4. The TI engine: memory

The engine runs from 32K memory expansion and SAMS. Its code: the kernel at >2000->2FFD (video, keyboard, disk, sound, pictures), the start-up code and font at >3000 (overwritten by the value stack once the game runs), and the resident engine at >A000->CFFF (the VM, output, input, UNDO, saving). Windows >D000, >E000 and >F000 (SAMS pages mapped in as needed) reach the story, pictures and the UNDO records. The RAM variables:

### SAMS pages

Pages 0-15 are the memory map itself (identity); 4-9 are never mapped (their windows are ROM and devices). The engine's own:


| Page | Name | Holds |
| --- | --- | --- |
| 16 | `UNDLST` | SAMS pages 16-19: the state at the newest snapshot |
| 20 | `UNDRNG` | pages 20-24: the snapshots' records |
| 25 | `SBPAGE` | SAMS pages 25-26: the last 50 lines shown |
| 27 | `HISPG` | SAMS page of the command history (window D during READ) |
| 28 | `PRPAGE` | first page of the pristine dynamic copy |
| 32 | `STPAGE` | first SAMS page of the story image |

The story occupies pages from 32; the picture area, then the sound area, follow it.

## 5. The workbench

The workbench is a 256K cartridge (FinalGROM 99). It runs from RAM: a resident part at >A000->AFFF, a kernel window at >2000->2FFE, and one overlay at a time at >B000, copied from its cartridge bank (the bank's last word holds its length).

## 6. F18A settings

Both programs refuse to start without an F18A or PICO9918 and SAMS. They use Text 80 with 30 rows and position attributes (VR50 >02), and the F18A's bitmap layer for pictures: VR32 the bitmap's address /64, VR33 and VR34 its position, VR35 0 (256 wide), VR36 96 rows, VR31 on with priority, fat pixels for 16 colours, and palette 32-47 (the picture's own colours). The workbench's text is palette 14 on 1, which its options change.

## 7. Known emulator differences

- js99er draws the bitmap layer doubled sideways in 80 columns (reported to its author).
- js99er's TI disk controller setting misreads double-density images; its "Generic Disk" setting reads them. TI's own controller reads single density only, so TXA's disks are 180K single density.
